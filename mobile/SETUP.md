# صراحة — إعداد API الاختباري وبناء Android

هذا المشروع يتضمن عميل Flutter أصليًا وواجهة PHP JSON تحت `deployment/api/v1/`. الواجهة ليست بديلًا مستقلًا لسكربت الموقع: تعتمد على `inc.php` وجداول الموقع ودواله. لا تتصل بقاعدة البيانات مباشرة من التطبيق. أبقِ ملفات موقع PHP وملف الإعداد وقاعدة البيانات الاختبارية خارج هذا المستودع.

> لا ترفع أي ملف إلى Hostinger، ولا تستخدم بيانات اعتماد الموقع أو قاعدة بيانات الإنتاج. أول طلب إلى API يحمّل `inc.php`، والذي يشغّل ترقية مخطط الموقع v12 عند الحاجة. كل الخطوات أدناه موجّهة إلى نسخة محلية منفصلة وقاعدة اختبار فارغة.

## 1) المتطلبات

- PHP **8.3** مع `pdo_mysql`, `mbstring` و`session` مفعّلة.
- MySQL أو MariaDB محلي منفصل. لا تمنح مستخدم الاختبار صلاحية على قاعدة الإنتاج.
- Flutter **3.32 أو أحدث** (Dart 3.8 أو أحدث)، Android SDK، وJava/JDK **17**.
- Android Emulator أو جهاز Android للاختبار. `10.0.2.2` هو عنوان الجهاز الافتراضي للوصول إلى خدمة الحاسوب المضيف من Android Emulator.

تحقق من نسخ PHP وإضافاته بـ `php -v` و`php -m`، ومن بيئة Android بـ `flutter doctor -v`. لم تُشغّل هذه الأدوات داخل بيئة إنشاء المشروع.

## 2) تجهيز بيئة البناء الخارجية (Flutter وJava وAndroid SDK)

1. ثبّت Git من [git-scm.com](https://git-scm.com/downloads).
2. ثبّت JDK 17. يمكن تنزيل Temurin 17 من [Adoptium](https://adoptium.net/temurin/releases/?version=17)، أو استخدام JDK 17 المرفق مع Android Studio إن كان مثبتًا. بعد التثبيت، تحقق بـ `java -version` وتأكد أن الإصدار 17. إذا اختار Flutter Java أخرى، حدّد مسار JDK 17 مرة واحدة عبر `flutter config --jdk-dir="/مسار/jdk-17"`، ثم افحص `flutter doctor -v`.
3. ثبّت Flutter SDK Stable باتباع الدليل الرسمي لنظامك: [Install Flutter](https://docs.flutter.dev/get-started/install). فكّ SDK في مجلد تملكه، وأضف مجلد `flutter/bin` إلى PATH، ثم افتح طرفية جديدة وتحقق بـ `flutter --version` و`dart --version`.
   - Windows: أضف المسار مثل `C:\src\flutter\bin` إلى متغير PATH من إعدادات النظام.
   - macOS/Linux: أضف `export PATH="$HOME/develop/flutter/bin:$PATH"` إلى ملف إعداد الطرفية (عدّل المسار حسب موقع SDK)، ثم أعد فتح الطرفية أو حمّل إعدادها.
4. نزّل Android Studio من [الموقع الرسمي](https://developer.android.com/studio/install) وشغّل Setup Wizard. من **SDK Manager** ثبّت Android SDK Platform التي يطلبها Flutter، و**Android SDK Platform-Tools**، و**Android SDK Command-line Tools (latest)**. ثبّت Android Emulator وصورة جهاز افتراضي إذا أردت الاختبار بالمحاكي. اترك إعداد SDK في المسار الافتراضي الذي يحدده Android Studio، أو استخدم المسار الذي يعرضه `flutter doctor -v`.
5. من الطرفية نفّذ `flutter doctor --android-licenses` واقبل التراخيص بعد مراجعتها، ثم نفّذ `flutter doctor -v`. عالج كل بند Android أحمر قبل متابعة البناء.
6. شغّل Android Studio/المحاكي أو صِل جهازًا فعليًا مع تفعيل USB debugging. عند بناء التطبيق على محاكي Android، عنوان الحاسوب المضيف هو `10.0.2.2`؛ أما الجهاز الفعلي فيستخدم IP الحاسوب على شبكة الاختبار.

## 3) أنشئ نسخة PHP وقاعدة اختبار محليتين

1. أنشئ مجلدًا جديدًا خارج المشروع مثل `/tmp/sarehny-test-site`، وانسخ إليه **ملفات سكربت PHP الأصلية** من أرشيف محلي تملكه. لا تنسخ `config.php` أو مجلدات الرفع/النسخ الاحتياطية من الموقع الحي، ولا تستخدم اتصال Hostinger. احتفظ بملفات PHP والمخطط `schema.sql` المتطابقة مع إصدار السكربت.
2. أنشئ قاعدة فارغة ومستخدمًا مخصصًا لها على MySQL المحلي. مثال SQL (استبدل كلمة المرور بقيمة محلية عشوائية، ولا تحفظها في Git):

   ```sql
   CREATE DATABASE sarehny_mobile_test
     CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
   CREATE USER 'sarehny_mobile_test'@'localhost' IDENTIFIED BY 'ضع-كلمة-مرور-محلية-عشوائية';
   GRANT ALL PRIVILEGES ON sarehny_mobile_test.* TO 'sarehny_mobile_test'@'localhost';
   ```

3. شغّل النسخة المحلية على قاعدة الاختبار فقط، وافتح `install.php` محليًا إذا لم يوجد `config.php`. أدخل بيانات القاعدة المحلية وأنشئ حساب إدارة تجريبيًا اصطناعيًا. المثبّت ينشئ `config.php` محليًا؛ لا تنقله إلى هذا المشروع ولا ترفعه.
4. انسخ API إلى جذر النسخة المحلية مع الحفاظ على المسار:

   ```sh
   mkdir -p /tmp/sarehny-test-site/api
   cp -a /path/to/project/deployment/api/v1 /tmp/sarehny-test-site/api/v1
   ```

   استبدل `/path/to/project` بمكان فك ضغط هذا المشروع. تأكد أن الملف المحلي هو `/tmp/sarehny-test-site/api/v1/index.php` وأن `inc.php` الخاص بالنسخة المحلية في جذر `/tmp/sarehny-test-site/`.
5. شغّل خادم PHP من جذر نسخة الاختبار:

   ```sh
   php -S 0.0.0.0:8080 -t /tmp/sarehny-test-site
   ```

   خادم PHP المضمّن لا يقرأ `.htaccess`، لكن التطبيق يستخدم `index.php?r=...` ولذلك لا يحتاج إعادة كتابة العناوين. افحص بدء الجلسة محليًا:

   ```sh
   curl -i 'http://127.0.0.1:8080/api/v1/index.php?r=session'
   ```

   المتوقّع استجابة JSON بحالة `200` و`user: null` قبل تسجيل الدخول. إذا ظهر خطأ قاعدة بيانات/مخطط، أوقف الاختبار وافحص **قاعدة الاختبار** وصلاحياتها وسجلات PHP؛ لا تغيّر وجهة اتصال إلى قاعدة حقيقية.

لا تستورد نسخة بيانات من المستخدمين أو الرسائل. أنشئ حسابًا تجريبيًا ورسائل اصطناعية من التطبيق. لا تستخدم تحليل الشخصية أثناء هذا الاختبار؛ النقطة الأصلية قد تتصل بمزوّد AI وتستهلك حصة أو تكلفة أُعدّت في سكربت الموقع.

## 4) عنوان API وإعدادات التطوير والإنتاج

عنوان API الافتراضي الموثق في `mobile/lib/src/api_config.dart` هو `https://sarehny.com/api/v1/`. يرسل Flutter الطلبات عبر `index.php?r=session` و`index.php?r=auth/login` ومسارات مماثلة، وليس عبر `/api/v1/session`؛ مسار URL المختصر يحتاج أن يسمح خادم الاستضافة بقراءة `.htaccess` و`mod_rewrite`. صفحات الموقع تُفتح من الأصل نفسه عبر PHP WebView. GitHub Actions يبني APK بهذا العنوان إذا كان `API_BASE_URL` فارغًا، ثم يختبر API الحقيقي قراءةً فقط، ويختبر session والواجهة على Android Emulator. يمكن تمرير `API_BASE_URL` لاستهداف HTTPS staging منفصل. لا تختبر عمليات كتابة على الإنتاج. للتطوير المحلي استخدم عنوان الخادم الذي شغّلته فعليًا، مثل `--dart-define=API_BASE_URL=http://10.0.2.2:8080/api/v1/` للمحاكي. Android يسمح بـHTTPS افتراضيًا؛ HTTP محصور في إعدادات debug.

## 5) فحوصات التطبيق وبناء Android

افتح الطرفية في مجلد `mobile/`:

```sh
flutter doctor -v
flutter pub get
flutter analyze
flutter test
flutter build apk --debug
```

ملفات Android وGradle Wrapper مضمنة. Gradle يستخدم JDK 17 ونسخة wrapper 8.14.3 وAndroid Gradle Plugin 8.11.1. لم يتوفر Flutter/Dart عند إعداد الحزمة، لذلك لا يوجد `pubspec.lock` مولّد بعد؛ ينشئه `flutter pub get`، وبعد مراجعته احتفظ به في Git لتثبيت نسخ الاعتماديات. إذا لم ينشئ Flutter `mobile/android/local.properties`، أضف إليه محليًا المسار الذي يعرضه `flutter doctor -v`:

```properties
flutter.sdk=/المسار/إلى/flutter
```

هذا الملف مستثنى من Git لأنه يختلف بين الأجهزة. ملف APK التجريبي يظهر في `mobile/build/app/outputs/flutter-apk/app-debug.apk`.

بناء APK دون تمرير `API_BASE_URL` يستخدم عنوان الموقع الأصلي `https://sarehny.com/api/v1/`. لا تستخدم رابط الإنتاج لاختبارات الكتابة؛ لاختبار التكامل مرّر رابط HTTPS لبيئة staging معزولة فقط. قبل توزيع إصدار فعلي، أعدّ توقيع Android بمفتاح تملكه في بيئتك الخارجية. لا تُضمّن keystore أو كلمات مروره في ZIP/Git؛ إعداد التوقيع غير مهيأ عمدًا هنا.

## 6) الاختبار السلوكي المتوقع

يستخدم APK عنوان API الإنتاجي افتراضيًا، وحتى تمرير قيمة `API_BASE_URL` فارغة لا يعطّل الاتصال؛ للتحقق الآمن من الكتابة استخدم عنوان staging وقاعدة اختبار منفصلين. سجّل الدخول بحساب الاختبار للوصول إلى الحساب والرسائل:

1. أنشئ حساب اختبار إذا كان `allow_register` مفعّلًا في قاعدة الاختبار، وإلا سجّل بحساب اختبار أنشأته محليًا.
2. أرسل رسالة اصطناعية إلى اسم المستخدم التجريبي، ثم اختبر ظهورها، والفلترة، والمفضلة، والإجابة، والإبلاغ والحذف.
3. سجّل الخروج وأعد فتح التطبيق؛ يجب ألا تبقى جلسة PHP المحلية بعد حذفها من التخزين الآمن.
4. إذا أوقفت PHP، يجب أن يعرض التطبيق خطأ اتصال مع خيار إعادة المحاولة.

يستخدم API جلسة PHP وCSRF، ويخزن معرّف الجلسة في `flutter_secure_storage`. يشمل Flutter صندوق الرسائل والإرسال وإدارة الحساب، مع رفع/حذف الصورة الشخصية عبر مساري `/account/avatar` و`/account/avatar/remove` (CSRF، تحقق من صورة فعلية، و10 MiB حدًا أقصى). تبويب «الموقع» يفتح صفحات PHP الفعلية داخل Android WebView مضبوط على الأصل نفسه؛ تُمرر جلسة PHP من التخزين الآمن عبر القناة الأصلية ولا تظهر في URL، ويُحدّث التطبيق الجلسة عند العودة. تظل صلاحيات الإدارة والتحقق من العمليات لدى PHP الأصلي. الروابط إلى مضيف آخر تفتح خارج التطبيق بلا تمرير جلسة PHP. ميزات مثل FCM/OAuth/إشعارات Android الأصلية تتطلب تكوين خدمات الموقع؛ لم تُفعّل أو تُدّعَ كوظائف Native.

### مصفوفة تغطية الميزات

| مجموعة الموقع | التغطية الحالية | التحقق |
| --- | --- | --- |
| تسجيل الدخول/التسجيل، الجلسة وCSRF، صندوق الرسائل وفلاتره وترقيم الرسائل القديمة، المفضلة والإجابة والحذف والإبلاغ | واجهات Flutter أصلية مرتبطة بعقد PHP | اختبارات الكود موجودة جزئيًا؛ لم يُختبر حساب staging بعد |
| إرسال نص/سؤال، الملف العام، إعدادات الاسم واسم المستخدم والبريد وكلمة المرور وحذف الحساب، المظهر الديناميكي المخزّن مؤقتًا | Flutter/API؛ رفع وحذف الصورة أُضيفا للمشروع | يحتاج نشر API على staging واختبار كتابة آمن |
| الصفحة الرئيسية ومحتواها، صفحات الملف العام والمقالات، من نحن، التواصل والدعم | تُعرض صفحات PHP الفعلية داخل WebView، وتستخدم بيانات الموقع الحية | الكود مضاف؛ لم يُختبر على جهاز Android أو ضد staging |
| التسجيل الصوتي ومؤثراته، مرفقات الصور والاستطلاع، لوحة الرسائل ذات الفرز/البحث/التصدير، الإحصاءات والمختبر الاجتماعي وصفحات المشاركة | تبقى وظائف الموقع الأصلية عبر WebView؛ ليست شاشات Flutter أصلية | تعتمد على إصدار الموقع وإعداداته الحالية |
| لوحة الإدارة وأقسامها | تُفتح داخل WebView للأعضاء الذين يعرض API لهم `is_admin`; يبقى فحص الدور وCSRF في PHP | لم يُختبر بحساب مدير على staging؛ لا يمنح التطبيق صلاحية جديدة |
| استعادة كلمة المرور، OAuth، FCM/إشعارات Android الأصلية | لم تُضف كوظائف جديدة؛ الاستعادة غير موجودة في تدفق PHP الذي راجعناه، والبقية تتطلب إعداد مزود الخدمة | غير متاحة/غير متحققة حاليًا |

هذه تغطية وظيفية مختلطة، وليست إعادة كتابة Native لكل صفحة؛ WebView يستضيف صفحات PHP الأصلية للحفاظ على الوظائف وعقد الخادم عند عدم وجود endpoint Flutter. لا يوجد ترحيل قاعدة بيانات ضمن التغييرات.

## 7) بناء APK تلقائيًا وتنزيله دون Android Studio

سير GitHub Actions في `.github/workflows/android-apk.yml` يشغّل PHP syntax lint، ويتحقق من تطابق أرشيف API مع مصدره، ثم ينفذ `flutter analyze` واختبارات Flutter، ويبني ويرفع APK debug، وبعده يتحقق من الموقع الحي ومسارات PHP بقراءات آمنة، ويختبر شاشة التطبيق والجلسة على Android Emulator. تُرفع الحزمة قبل اختبارات الخدمة كي تبقى متاحة حتى إن كشف الفحص أن نشر الموقع ناقصًا. يبدأ تلقائيًا عند تغييرات `mobile/` أو `deployment/api/v1/` أو أرشيف API أو Workflow؛ ويمكن تشغيله يدويًا من **Actions → Build Android APK (production or staging) → Run workflow** وترك `api_base_url` فارغًا لاستخدام الإنتاج، أو تحديد HTTPS staging. الـArtifact صالح 14 يومًا، وهو debug وغير موقّع. لا يرفع الـWorkflow ملفات إلى Hostinger ولا يغيّر قاعدة البيانات.

**اختبار API على staging داخل Android:** يشغّل `integration_test/staging_smoke_test.dart` التطبيق على Android Emulator ويسجّل الدخول بالحساب المخصص. يفتح شاشة الحساب، يغيّر الاسم الظاهر مؤقتًا عبر واجهة Flutter، يتحقق من القيمة على API ثم يعيد الاسم الأصلي؛ ويفتح صندوق الوارد، ويرسل رسالة اختبار إلى الحساب نفسه، ويتحقق من ظهورها ثم يحذفها ويسجل الخروج. ينظف الاختبار الاسم والرسالة اللذين غيّرهما إذا تعثر بعد بدء العملية. لا يُشغّل هذا الاختبار على الإنتاج؛ يغيّر اسم حساب staging مؤقتًا ثم يعيده، ولا يغيّر كلمة المرور أو بيانات أي مستخدم إنتاجي.

لتشغيله بأمان، أنشئ PHP staging وقاعدة بيانات منفصلة من نسخة اختبارية من المخطط، وأنشئ حسابًا مخصصًا غير إداري للاستعمال الآلي واجعل استقبال الرسائل مفعّلًا عليه. في إعدادات مستودع GitHub، أضف أسرارًا باسم `SAREHNY_STAGING_USERNAME` و`SAREHNY_STAGING_PASSWORD`، ثم شغّل يدويًا **Actions → Build Android APK (production or staging) → Run workflow**، وأدخل عنوان staging HTTPS ينتهي بـ`/api/v1/` وفعّل `run_staging_integration`. لا تضع كلمة المرور في عنوان URL أو مستودع Git أو سجل المحادثة. يرفض فحص Workflow عنوانًا لا يبدو عنوان اختبار، لكن يجب أيضًا التأكد بشريًا أن النطاق وقاعدة البيانات معزولان عن الإنتاج.

تشغيل `38092972775` سجل تاريخي لنسخة APK offline ولا يمثل فحص اتصال. التشغيل `38096877000` بنى ورفع artifact رقم 21 بنجاح، لكن اختبار Android Emulator لم يبدأ لأن صورة Android SDK انتهت بمساحة القرص؛ يعالج Workflow الحالي مساحة المحاكي ويرفع الـAPK قبل فحوص الخدمة. لم تُنشر تغييرات API إلى Hostinger ولم تُعدّل قاعدة الإنتاج.

## 8) تنزيل المشروع كاملًا أو ZIP

- لتنزيل المصدر مع المجلدات والمسارات من v0، استخدم قائمة النقاط الثلاث أعلى المشروع واختر **Download ZIP**. يشمل المشروع ملف CI. لفتح Flutter، فك الضغط وافتح مجلد `mobile/` في الطرفية أو Android Studio.
- أو استخدم GitHub المتصل مع المشروع، واستنسخ الفرع الذي يحتوي التغييرات.
- يحجب `.gitignore` ملفات الإعداد ومخرجات Flutter/Gradle ومفاتيح Android وقواعد البيانات المحلية. لا تُدرج `local.properties`, `config.php`, قواعد بيانات أو dumps، ملفات `.env`, مفاتيح توقيع، `google-services.json` أو بيانات مستخدمين في ZIP/Git. `pubspec.lock` غير مولّد هنا؛ يولّده `flutter pub get` في CI قبل التحليل والبناء.

## حالة التحقق وحدودها

لم أرفع أو أعدّل أي ملف على Hostinger أو قاعدة البيانات. من الأدلة الحية: `session` يُنفّذ عبر `index.php?r=...` ويعيد JSON، بينما `r=app-theme` يرجع JSON من fallback الخاص بالتطبيق (`code:not_found`). إذن عنوان Flutter وصيغة query يصلان إلى PHP؛ الملف الذي يخدم `api/v1/index.php` لا يحتوي حاليًا على معالج `app-theme`، وليس هذا خلل rewrite أو حاجة لتغيير عنوان التطبيق. لا يمكن من HTTPS وحده التمييز بين نسخة API قديمة وdocument root مختلف، ولا قراءة الملف أو checksum المنشور. `theme-public` ليس route في عميل Flutter ولا في مصدر API المحلي؛ العقد المستخدم هو `app-theme`، لذلك لا تضف alias غير مطلوب.

**التعديل اليدوي المقترح بعد نسخة احتياطية، دون استبدال الملف:** في Hostinger File Manager نزّل نسخة من **`<document-root>/api/v1/index.php`** (غالبًا `public_html/api/v1/index.php`) واحفظها خارج مجلد الموقع. قارنها بـ`deployment/api/v1/index.php`، ثم أضف فقط كتلة معالج المظهر إن لم تكن موجودة؛ أبقِ كل الدوال والمسارات الأخرى كما هي. اعتمد `theme_fields()` و`setting()` الموجودتين في `inc.php` و`api_ok()` ومعالجة المسار الحالية. ضع الدالة المساعدة قرب دوال API الأخرى، قبل قراءة/dispatch المسارات:

```php
function api_public_theme() {
  $colors = [];
  foreach (theme_fields() as $key => $field) {
    $value = (string)setting('theme_' . $key, $field[1]);
    $colors[$key] = preg_match('/^#[0-9a-fA-F]{6}$/D', $value) ? strtolower($value) : $field[1];
  }
  return ['colors' => $colors, 'radius' => max(0, min(24, (int)setting('ui_radius', '8')))];
}
```

وقبل معالج `/session` أو fallback `not_found` داخل dispatch، أضف:

```php
if ($method === 'GET' && $route === '/app-theme') {
  api_ok(['theme' => api_public_theme()]);
}
```

إذا اختلف هيكل الملف المنشور عن هذا، لا تلصق البلوك عشوائيًا؛ طابق موضع fallback وصيغة المتغيرات أولًا. احفظ الملف بعد التعديل مع إبقاء `inc.php` و`.htaccess` وسائر ملفات الموقع وقاعدة البيانات دون تغيير. تحقق بعدها من `GET https://sarehny.com/api/v1/index.php?r=app-theme`؛ المطلوب `200` وJSON فيه `ok:true` و`theme.colors` و`theme.radius`. إذا استمر `not_found`، أعد الملف الاحتياطي وافحص أن المسار هو document root الفعلي وأن Hostinger لا يقدّم نسخة PHP مخزنة مؤقتًا. لا يمكنني تنفيذ هذه الخطوات داخل v0.
